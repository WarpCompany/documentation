<Note>
  **Roadmap.** Warp Bridge is a design proposal and is not yet available. This page describes planned behavior, which may change.
</Note>

Warp Bridge is designed as two layers: on-chain contracts that lock, validate and settle orders, and a permissionless network of solvers that fill them from their own liquidity.

## Protocol layer

Each supported chain would host two contracts: **WarpSource** and **WarpDestination**.

### WarpSource

WarpSource would start every transfer. When a user creates an order, it would lock the user's tokens, assign a deterministic order ID, store the order state and emit the event that solvers watch for. Locked tokens could leave the contract in only two ways: released to the solver after a verified fulfillment, or refunded to the user after a cancellation.

### WarpDestination

WarpDestination would validate fulfillment attempts. A solver would send the destination tokens to the recipient and submit the order parameters. The contract would rebuild the order ID, check that the order is neither fulfilled nor canceled, and mark it fulfilled. It would then send an authenticated message to WarpSource to release the locked tokens to the solver.

### Deterministic order IDs

Each order ID would be a hash of the user, tokens, chains, amounts and security parameters, so an order can't be replayed, spoofed or altered.

## Solver layer

Solvers would be independent market makers and bots. They would watch WarpSource for new orders, price the risk off-chain, and fill orders they find profitable by paying the recipient on the destination chain. Solvers would earn the spread between the input and output amounts and carry chain-reorg and messaging-finality risk, mitigated by confirmation thresholds, replay protection and contract-level checks.

## Order lifecycle

<Steps>
  <Step title="Create">
    The user chooses chains, tokens and amount. WarpSource locks the tokens and emits the order.
  </Step>
  <Step title="Evaluate">
    Solvers check liquidity, gas, finality and profit. Several may compete for the same order.
  </Step>
  <Step title="Fulfill">
    A solver pays the recipient on the destination chain and WarpDestination marks the order fulfilled. The user now has their tokens.
  </Step>
  <Step title="Settle">
    WarpDestination sends a release message to WarpSource, which releases the locked tokens to the solver.
  </Step>
</Steps>

## Cancellation

Cancellation would follow the same path as settlement, in reverse. While an order is unfilled, the user would request cancellation on WarpDestination. WarpDestination would mark the order canceled — so no solver can fill it afterwards — and send a cancel message to WarpSource, which refunds the locked tokens to the user.

## Risk model

- **Users** — funds would sit in non-custodial contracts and could be reclaimed by canceling an unfilled order. Users would still carry smart contract risk and the risk of the cross-chain messaging layer.
- **Solvers** — would carry reorg and finality risk between paying the recipient and receiving the released tokens.
